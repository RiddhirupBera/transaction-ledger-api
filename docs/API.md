# Transaction Ledger API — API Documentation

Base URL: `http://localhost:3000/api` in development, or `http://localhost:8080/api` in full-stack Docker mode. Send JSON with `Content-Type: application/json`.

All money input/output uses fixed two-decimal **strings**, for example `"12.34"`. Amounts must be positive, at most `"90071992547409.91"`, and have exactly two decimal places. JSON numbers, exponent notation, leading zeros, signs, zero amounts, and extra precision are rejected. Internally amounts and balances are safe integer minor units, never floating-point amounts. Balances may equal zero. Request bodies reject unknown properties. IDs are 24-character MongoDB ObjectIds generated by the server. Dates are ISO 8601 strings.

## Field naming

Assessment names `created_at`, `account_id`, and `reference_id` are included in applicable responses. Original `createdAt`, `accountId`, and `referenceId` aliases remain supported for the dashboard. Examples below may use either style. Ordinary posting accepts either `reference_id` or `referenceId`. Transfers accept `source_account_id` / `sourceAccountId`, `destination_account_id` / `destinationAccountId`, and `reference_id` / `referenceId`. Supply only one spelling for each field; sending both is a 400 validation error. Public inputs cannot override IDs, timestamps, balances, or internal minor-unit fields. See [assumptions](ASSUMPTIONS.md).

## Endpoints

| Method | Path | Input | Success |
|---|---|---|---|
| POST | `/accounts` | `{ "name": "Operations" }` | 201, `{ "data": Account }` |
| GET | `/accounts` | None | 200, `{ "data": Account[] }`, newest first |
| GET | `/accounts/:id/balance` | ObjectId path parameter | 200, `{ "data": { "accountId": "…", "balance": "0.00" } }` |
| POST | `/accounts/:id/transactions` | `{ "type": "credit", "amount": "12.34", "description": "Deposit", "referenceId": "deposit-001" }` | 201, `{ "data": TransactionWithBalance }` |
| POST | `/transfers` | Source/destination IDs, amount, reference, optional description | 201 with both balances and both ledger entries; see below |
| GET | `/accounts/:id/transactions?type=credit&page=1&limit=10` | Optional type, page, limit | 200, `{ "data": Transaction[], "pagination": { "page": 1, "limit": 10, "total": 1, "totalPages": 1 } }` |

An account includes `{ "id": "…", "name": "Operations", "balance": "0.00", "created_at": "…", "createdAt": "…" }`.
A transaction includes `{ "id": "…", "account_id": "…", "type": "credit", "amount": "12.34", "description": "Deposit", "reference_id": "deposit-001", "created_at": "…" }`, plus equivalent `accountId`, `referenceId`, and `createdAt` aliases. The balance endpoint includes both `account_id` and `accountId`. Posting adds `balance`, representing the balance after that posting at its commit; another request may change it afterward. Internal `amountMinor`, `balanceMinor`, and `__v` are not exposed.

`name` and `referenceId` are trimmed and must not be blank. `description` is optional and defaults to `""`. Type is exactly `credit` or `debit`. The path determines the account; supplying `accountId` in a posting body is invalid.

History defaults to page 1, limit 10. Page must be a positive safe integer, limit must be 1–100, and the calculated offset must remain a safe integer. Query values must be ordinary decimal integer strings; duplicate or unknown query parameters are rejected. Omit `type` for both types; an empty `type=` is invalid. History sorts by `createdAt DESC, _id DESC`, including timestamp ties, with indexes for filtered and unfiltered access. An out-of-range page returns an empty array. Empty history returns `totalPages: 0`. Results and count are separate reads and can reflect intervening concurrent commits; offset pagination can shift when new entries arrive.

## Errors

All errors have the same envelope:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid request",
    "details": [{ "path": "amount", "message": "Use a decimal string with exactly two places, e.g. 12.34" }]
  }
}
```

`details` is included only for Zod validation errors.

| Status | Codes | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR`, `INVALID_JSON`, `BODY_TOO_LARGE` | Invalid fields, IDs, queries, JSON, or body over 32 KiB |
| 404 | `ACCOUNT_NOT_FOUND`, `NOT_FOUND` | Valid but nonexistent account ID, or unsupported route/method |
| 409 | `DUPLICATE_REFERENCE` | Reference already exists for this account; no new posting |
| 409 | `WRITE_CONFLICT` | Bounded transient retries exhausted; retry with the same reference |
| 409 | `COMMIT_OUTCOME_UNKNOWN` | Commit could not be confirmed; inspect history for the reference before retrying |
| 422 | `INSUFFICIENT_BALANCE`, `BALANCE_OVERFLOW`, `SAME_ACCOUNT_TRANSFER` | Posting would make balance negative, exceed safe integer range, or transfer to the same account |
| 503 | `DATABASE_UNAVAILABLE` | Readiness check cannot reach MongoDB |
| 500 | `INTERNAL_ERROR` | Unexpected infrastructure/server error; details are not exposed |

Repeated references return 409 even when the payload matches. They do not replay the previous success response. Reference uniqueness is per account, case sensitive, after trimming. Reuse the **same** reference for a retry to prevent double posting. If an uncertain commit has not yet appeared in history, its outcome may still be pending; a retry must still use the same reference.

There are no direct balance-update routes, transaction edit/delete routes, or account-delete routes.

## Atomicity and concurrency

Each posting uses a Mongoose session and explicit MongoDB multi-document transaction with snapshot read concern and majority write concern. It reads the account and checks the reference, calculates the balance using `BigInt`, validates the result, writes the account, inserts the transaction, and commits. Every successful posting changes the shared account document. Competing snapshots on the same account therefore encounter a write conflict rather than silently overwriting a balance or both spending the same funds. A retry starts a fresh transaction, rereads the balance, and repeats all business checks. Failed inserts roll back the account write, and rejected debits create no history entry. Operations within a transaction execute sequentially.

The runner uses the core API to bound application-level retries: at most **5 whole-transaction attempts** for errors labeled `TransientTransactionError`, with exponential backoff plus jitter. Business errors and MongoDB duplicate key code `11000` are never retried, even if also labeled transient. A unique `{ accountId: 1, referenceId: 1 }` index is the final protection against reference races; the preliminary lookup improves the error response but does not replace the index.

`UnknownTransactionCommitResult` retries only the same commit, up to **3 commit attempts**, without reexecuting the body. If still uncertain, the API returns `COMMIT_OUTCOME_UNKNOWN`; the transaction might have committed. This differs from a normal aborted business failure. Commit commands have a 5-second server time limit; retry counts bound application attempts, not overall network wall time. Sessions are always ended. These label-based retry rules follow [MongoDB's transaction API guidance](https://www.mongodb.com/docs/manual/core/transactions-in-applications/).

Startup requires a replica set or sharded cluster, creates declared indexes, then inspects MongoDB's actual index catalog. It refuses to listen if the full, non-sparse, non-partial unique `(accountId, referenceId)` index is absent or index creation fails (including preexisting duplicate data). It does not silently drop or replace conflicting indexes.

## curl examples

Start the database and API using the README. These examples use `jq` to capture the created ID:

```sh
BASE=http://localhost:3000/api
ACCOUNT_ID=$(curl --fail-with-body -sS -X POST "$BASE/accounts" \
  -H 'Content-Type: application/json' \
  -d '{"name":"Operations"}' | jq -r '.data.id')

curl -sS "$BASE/accounts"
curl -sS "$BASE/accounts/$ACCOUNT_ID/balance"

curl -i -X POST "$BASE/accounts/$ACCOUNT_ID/transactions" \
  -H 'Content-Type: application/json' \
  -d '{"type":"credit","amount":"100.00","description":"Opening deposit","referenceId":"deposit-001"}'

curl -i -X POST "$BASE/accounts/$ACCOUNT_ID/transactions" \
  -H 'Content-Type: application/json' \
  -d '{"type":"debit","amount":"25.50","description":"Invoice payment","referenceId":"payment-001"}'

curl -sS "$BASE/accounts/$ACCOUNT_ID/balance"
# balance: "74.50"
curl -sS "$BASE/accounts/$ACCOUNT_ID/transactions?page=1&limit=10"
curl -sS "$BASE/accounts/$ACCOUNT_ID/transactions?type=debit&page=1&limit=10"

# 409 duplicate reference, no balance change
curl -i -X POST "$BASE/accounts/$ACCOUNT_ID/transactions" \
  -H 'Content-Type: application/json' \
  -d '{"type":"credit","amount":"100.00","referenceId":"deposit-001"}'

# 422 insufficient balance, no new transaction
curl -i -X POST "$BASE/accounts/$ACCOUNT_ID/transactions" \
  -H 'Content-Type: application/json' \
  -d '{"type":"debit","amount":"1000.00","referenceId":"too-large-001"}'
```

## Money transfers

`POST /api/transfers` implements the assessment bonus. Example body:

```json
{
  "source_account_id": "SOURCE_OBJECT_ID",
  "destination_account_id": "DESTINATION_OBJECT_ID",
  "amount": "30.00",
  "description": "Transfer to reserves",
  "reference_id": "transfer-001"
}
```

The IDs above are placeholders: replace them with actual account IDs. Both accounts must exist (404 otherwise), differ (422 otherwise), and have valid balances. The source must have enough funds and the destination must remain within the safe integer limit (422). Amount follows the same positive two-decimal string contract as posting. Reference is required and must be unused in **both** participating accounts; an existing ordinary posting also reserves that account's reference. Duplicate references return 409 without changing either account.

On success, HTTP 201 returns:

```json
{
  "data": {
    "reference_id": "transfer-001",
    "referenceId": "transfer-001",
    "amount": "30.00",
    "source": { "id": "SOURCE_OBJECT_ID", "name": "Operations", "balance": "70.00", "created_at": "...", "createdAt": "..." },
    "destination": { "id": "DESTINATION_OBJECT_ID", "name": "Reserves", "balance": "80.00", "created_at": "...", "createdAt": "..." },
    "transactions": [
      { "id": "DEBIT_OBJECT_ID", "account_id": "SOURCE_OBJECT_ID", "accountId": "SOURCE_OBJECT_ID", "type": "debit", "amount": "30.00", "description": "Transfer to reserves", "reference_id": "transfer-001", "referenceId": "transfer-001", "created_at": "...", "createdAt": "..." },
      { "id": "CREDIT_OBJECT_ID", "account_id": "DESTINATION_OBJECT_ID", "accountId": "DESTINATION_OBJECT_ID", "type": "credit", "amount": "30.00", "description": "Transfer to reserves", "reference_id": "transfer-001", "referenceId": "transfer-001", "created_at": "...", "createdAt": "..." }
    ]
  }
}
```

Timestamps above stand for real ISO strings. The example assumes source 100.00 and destination 50.00 before the transfer. The response's two balances reflect this transfer, and can subsequently change through other postings.

One session transaction reads both accounts, checks the shared reference, validates both next balances, saves accounts in ascending ObjectId order, and sequentially inserts a source debit and destination credit with the same reference and creation timestamp. A failure on any write or either insert rolls everything back. No intermediate balance update or lone transfer entry can commit. Stable account write order reduces contention, while shared account writes and the existing bounded transient retry policy protect races with transfers and ordinary debits/credits.

Both entries appear in normal account history and remain immutable. No separate transfer collection or edit/delete route is introduced. The endpoint does not assume global uniqueness of reference IDs: transfers involving completely different accounts may reuse a reference. For uncertain commits, inspect both histories and retry only with the original reference.

A curl walkthrough using a new account pair and `jq`:

```sh
BASE=http://localhost:3000/api
SOURCE_ID=$(curl --fail-with-body -sS -X POST "$BASE/accounts" -H 'Content-Type: application/json' -d '{"name":"Transfer source"}' | jq -r '.data.id')
DESTINATION_ID=$(curl --fail-with-body -sS -X POST "$BASE/accounts" -H 'Content-Type: application/json' -d '{"name":"Transfer destination"}' | jq -r '.data.id')
curl --fail-with-body -sS -X POST "$BASE/accounts/$SOURCE_ID/transactions" -H 'Content-Type: application/json' -d '{"type":"credit","amount":"100.00","reference_id":"source-opening"}'
curl --fail-with-body -sS -X POST "$BASE/accounts/$DESTINATION_ID/transactions" -H 'Content-Type: application/json' -d '{"type":"credit","amount":"50.00","reference_id":"destination-opening"}'
curl --fail-with-body -sS -X POST "$BASE/transfers" \
  -H 'Content-Type: application/json' \
  -d "{\"source_account_id\":\"$SOURCE_ID\",\"destination_account_id\":\"$DESTINATION_ID\",\"amount\":\"30.00\",\"description\":\"Transfer to reserves\",\"reference_id\":\"transfer-001\"}"
curl -sS "$BASE/accounts/$SOURCE_ID/balance"
curl -sS "$BASE/accounts/$DESTINATION_ID/balance"
```

Expected balances are 70.00 and 80.00. Repeating the same transfer request yields 409 with unchanged balances.


## Readiness

`GET /api/health` returns 200 with `{"data":{"status":"ok"}}` when MongoDB is connected and responds to a ping. It returns 503 with `error.code: "DATABASE_UNAVAILABLE"` otherwise. This endpoint exposes no account or transaction data and is used by the full-stack Docker health checks.
